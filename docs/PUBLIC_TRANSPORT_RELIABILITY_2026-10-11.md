# Swiss public-transport reliability — implementation and remaining work

Reviewed 11 October 2026. This is the current implementation note for the owner's request to use public Swiss data, explain required tickets/bicycle conditions/fares, and identify what remains before publication. It supersedes the nationwide-fare dependency and five-source monitoring descriptions in the [previous release](FARES_PROFILES_AND_MONITORING_2026-10-11.md). The app remains owner-private.

## Conclusions on the owner's questions

1. **Using the national transport data is the right foundation.** OJP and SBB draw on the Swiss timetable/realtime ecosystem, but OJP is an independently configured journey planner. Sharing upstream data does not prove identical routing, transfer treatment, operator coverage or update latency. Measure agreement on the same dated services and keep scheduled, estimated, stale and missing information distinct.
2. **Information-only ticket advice is feasible.** Selling tickets or checking available bicycle spaces is not required to explain the ticket, requirement and supported fare. Keep permission, passenger entitlement, bicycle ticket, reservation and capacity separate. This release does not reserve or sell anything.
3. **The owner is right that substantial local information is public.** A production sales API is not a prerequisite for computing reviewed standard local fares. We need the actual route/zone/product/date/profile mapping as well as the published amount. Reduced local fares are not always half the adult price.
4. **SBB's coverage is an achievable direction, not today's delivered scope.** Published standard prices can be implemented network by network. Dynamic saver offers and comprehensive national quoting require a suitable production information interface or an equivalently complete current tariff engine. The OJP Fare cookbook still describes integration/test data; its public availability is not proof of production price accuracy.
5. **Work with local companies on precise gaps.** Use their public data first. Ask for corrections to conflicting rules, missing machine-readable joins and change notices, and share exact dated examples through the existing downloadable journey report. No operator has been contacted by this work.

These include internal, foreign and nonoperator registry entities; they are **not 1,306 individually audited transport companies**. Future realtime projects are explicitly not marked live. Inventory coverage does not imply every fare or bike rule is reviewed.
- [Live NOVA linked-data query evidence](research/NOVA_LOD_PUBLIC_FARE_AUDIT_2026-10-11.json): 23,812 priced zone objects were found, but no inbound links binding them to the required tariff/pay-level objects and no verified effective dates. Those numbers cannot safely be assigned to a local journey. Public route/zone topology remains useful.
- [TPG join evidence](research/TPG_ZONE10_STOP_EVIDENCE_2026-10-11.json) and [reproducible extraction script](research/derive_tpg_zone10_evidence.py). Outputs are review candidates; the script never extends the app's fare coverage.

The OSDM offline catalogue does not establish a complete current local-fare solution: its documented route focus is international distribution, metadata is old, and the actual current archive validity was not verified. A NOVA PROD API listing is discoverable, but anonymous/free production access has not been established. The useful next question is **read-only production price information**, rather than assuming the information-only app needs the full ticket-sales contract.

## Automatic acquisition before expiry

The existing linked schedule remains **Monday–Friday, 08:30 Europe/Zurich**. It calls the private Site's `POST /api/maintenance/check` with the explicit maintenance intent, then reads `GET /api/maintenance/status`. The persistent daily lease prevents retries from multiplying provider calls. No new key, subscription, operator message or ticket-sale integration was added.

- `/api/maintenance/status` lists source status, hashes, timestamps, retrieval errors, review boundaries and canary history. Not-yet-visited sources are pending. Up to eight due sources are fetched each run, oldest first; near-expiry “daily due” does not mean all 24 are downloaded every day.
- `/api/maintenance/sources/{id}` supplies the last retained HTML/PDF/JSON candidate when `candidateSaved` is true. Sources above 750 kB retain their official URL/hash but no downloadable copy; all retrievals are bounded at 2.5 MB. These private review copies are not published into GitHub.
- The GitHub **Tariff expiry watch** still runs daily at 06:15 UTC. It now covers operator/route sources too. Warnings start at 60 days or an earlier `reviewBy`; urgency escalates at 30, 14 and 7 days, then expired. A red renewal check calls for a review, not an arbitrary date extension.
- Download and inspect successor tariffs as soon as they are published. Public advance examples already found include Arcobaleno's 13 December 2026 tariff and Mobilis's successor landing page. Reconcile scope and effective dates before activation.
- Update amounts/rules, route coverage and reviewed dates together; test both sides of the change; deploy the matching app and commit the evidence. If a source cannot be renewed, preserve explicit expired/unknown results and its operator link.

A raw document hash only detects a change. Automated retrieval cannot certify that every tariff exception has been interpreted correctly. Changes are review candidates, and source freshness is separate from live vehicle prediction freshness.
